# Extract ingestion logic into `ai/ingestion/` subpackage

**Status:** approved
**Date:** 2026-06-08
**Scope:** structural refactor of `apps/os_lms/os_lms/os_lms/ai/`, no behaviour change

## Goal

Move all ingestion logic that is currently flattened at the top of `apps/os_lms/os_lms/os_lms/ai/` into a dedicated `ingestion/` subpackage, so the `ai/` directory mirrors the pattern already used by `simulations/` and `tutor/`. Each AI feature becomes a self-contained subpackage with its own `api.py`, services, and scheduler.

This is a pure structural refactor: no behaviour, signatures, or stored data change. Endpoints stay whitelisted, the OpenAPI spec stays at the same aggregator function, only the dotted path (and therefore the URL) of ingestion endpoints changes.

## Current state

```
ai/
├── api.py                  # mixed: ingestion endpoints + chat + OpenAPI aggregator
├── ingestion_service.py    # class IngestionService
├── ingestion.py            # RAG primitives: chunking, hashing, normalize, get_settings
├── scheduler.py            # reindex_lesson_content daily job
├── simulations/            # self-contained subpackage
├── tutor/                  # self-contained subpackage
└── utils/                  # shared LLM/RAG utilities
```

Three external touch points reference these modules:

- `apps/os_lms/os_lms/hooks.py:157` — scheduled task path
- `apps/os_lms/os_lms/os_lms/ai/tutor/tutor_ai.py:7` — imports `IngestionService`
- `frontend/src/oslms/composables/useLessonIngestion.js:35` — calls the endpoint URL

The OpenAPI spec at `ai/api.py::get_lmsa_openapi_spec` hardcodes the three `/api/method/os_lms.os_lms.ai.api.*` paths.

## Target state

```
ai/
├── __init__.py
├── api.py                  # SLIM: ask_lmsa_chat + get_lmsa_openapi_spec only
├── _lesson_access.py       # NEW private helper: load_lesson()
├── ingestion/              # NEW subpackage
│   ├── __init__.py         # re-exports IngestionService
│   ├── api.py              # start_lesson_ingestion, get_lesson_ingestion_status
│   ├── service.py          # ex ingestion_service.py → class IngestionService
│   ├── pipeline.py         # ex ingestion.py → material_hash, normalize_lesson_text, chunk_text, get_settings
│   └── scheduler.py        # ex ai/scheduler.py → reindex_lesson_content
├── simulations/            # unchanged
├── tutor/                  # unchanged
└── utils/                  # unchanged
```

### Why these names

- `service.py` / `pipeline.py` / `scheduler.py` / `api.py` follow the semantic-short convention used in `simulations/` (`orchestrator.py`, `tasks.py`, `api.py`). It keeps imports tidy: `from os_lms.os_lms.ai.ingestion.service import IngestionService` instead of the redundant `ai.ingestion.ingestion_service`.
- `_lesson_access.py` is a leading-underscore private module. It exists only to break a would-be circular import: after the move, `ai/api.py` (chat) and `ai/ingestion/api.py` (ingestion) both call `load_lesson()` for permission checks, so the helper must sit above both.

## Path changes

### Python imports

| Old | New |
|---|---|
| `from os_lms.os_lms.ai.ingestion_service import IngestionService` | external callers: `from os_lms.os_lms.ai.ingestion import IngestionService` (via `__init__` re-export). Internal callers inside `ingestion/`: `from .service import IngestionService` |
| `from .ingestion import material_hash, normalize_lesson_text` (inside `ai/api.py`) | becomes `from .pipeline import material_hash, normalize_lesson_text` (inside `ai/ingestion/api.py`) |
| `from .ingestion_service import IngestionService` (inside `ai/scheduler.py`) | becomes `from .service import IngestionService` (inside `ai/ingestion/scheduler.py`) |

### Endpoint URLs (Frappe whitelisted method paths)

| Old | New |
|---|---|
| `os_lms.os_lms.ai.api.start_lesson_ingestion` | `os_lms.os_lms.ai.ingestion.api.start_lesson_ingestion` |
| `os_lms.os_lms.ai.api.get_lesson_ingestion_status` | `os_lms.os_lms.ai.ingestion.api.get_lesson_ingestion_status` |
| `os_lms.os_lms.ai.api.ask_lmsa_chat` | unchanged (stays in `ai/api.py`) |
| `os_lms.os_lms.ai.api.get_lmsa_openapi_spec` | unchanged (stays in `ai/api.py`) |

### Scheduled task path (hooks.py)

| Old | New |
|---|---|
| `os_lms.os_lms.ai.scheduler.reindex_lesson_content` | `os_lms.os_lms.ai.ingestion.scheduler.reindex_lesson_content` |

## External callers to update

1. **`apps/os_lms/os_lms/hooks.py:157`** — replace the scheduler dotted path inside the daily schedule entry.
2. **`apps/os_lms/os_lms/os_lms/ai/tutor/tutor_ai.py:7`** — update the `IngestionService` import to the new module path.
3. **`frontend/src/oslms/composables/useLessonIngestion.js:35`** — update the `url:` value to the new endpoint path.

The Vue build artifact at `lms/public/frontend/assets/LessonForm-*.js` also embeds the old URL, but it is regenerated by `yarn build` and is not edited by hand.

## OpenAPI spec

`get_lmsa_openapi_spec` keeps its aggregator role inside `ai/api.py`. Inside the returned `paths` dict, the two ingestion path keys are rewritten to the new dotted paths. The chat path key stays the same. No structural change to the spec shape — only string updates.

## Backward compatibility

None. There is no shim or alias at the old endpoint URL. Rationale:

- The SPA is the only known consumer of `start_lesson_ingestion` / `get_lesson_ingestion_status`, and we update it in the same change.
- The Frappe Desk is sysadmin-only in this project, so no user-facing Desk view relies on these paths.
- Carrying a shim leaves dead code that has to be removed later.

If an unknown external integration exists, the call will fail with a clear `frappe.does_not_exist` error rather than silently behaving differently. That is an acceptable failure mode for an internal refactor.

## Non-goals

- The chat endpoint `ask_lmsa_chat` is not relocated. It stays in `ai/api.py` for now even though chat-over-RAG is conceptually a separate feature; extracting it is a future refactor that this work does not block.
- The `get_lmsa_openapi_spec` aggregator is not split per-feature. Each AI subpackage does not yet export its own OpenAPI fragment; that is a future refinement out of scope here.
- `ai/utils/` is untouched.
- No new tests are added. There is no existing test for the ingestion endpoints today, and the refactor preserves behaviour; adding tests is a separate piece of work.

## Risks and mitigations

- **Frappe URL caching / cached fixtures.** None known for whitelisted method paths — the path is resolved per call from the module system.
- **Missed reference.** Mitigated by grepping for the four moving symbols (`IngestionService`, `reindex_lesson_content`, `start_lesson_ingestion`, `get_lesson_ingestion_status`) and the old module paths before declaring done.
- **Circular import after the move.** Mitigated by extracting `load_lesson` into `_lesson_access.py` before `ai/ingestion/api.py` is created.
